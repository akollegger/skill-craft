# Multi-skill distillation: lessons learned from experience

Status: exploratory, 2026-10-13. A note, not a decision. It may become an amendment to ADR-003 (the unit of distillation, the held-out design) and an ADR for harness-based distillation, which may replace the memory service as the distiller entirely. Nothing here is built.

## Why this note

The distillation in ADR-003 and in the code has one target: one skill per experiment, distilled from the trials that reached one goal. In the invented world that leaves most of what a run learns on the table. A search, whether random, strategic or reasoned, crafts many things on the way to a goal, and each craft the agent sees is a discovered recipe. What an agent can learn there has several shapes:

- **A catalog:** arrangement to item, for everything the search made, wanted or not.
- **Chains:** which item feeds which craft (`vriobeno` takes two crafts).
- **A generalized shape:** a rule across recipes that predicts one nobody tried.

The learning in an invented world is potentially larger than in the faithful world (where recall dominates) or the perturbed world (where deviations from a prior dominate), because everything must be discovered and nothing is known in advance.

## What the current design assumes

- ADR-003 §2.5: one skill per experiment, from the conversations of the trials that reached their goal; the teacher is recorded only on gap goals.
- `assertSameTask` (`src/loop/transcript.ts`) refuses recordings of different goals or worlds.
- Failed trials, and the by-products of successful ones, never reach the distiller.
- A student arm installs one skill, and `score.json` records one skill hash.
- The critic's rubric already asks whether a skill is a rule or a fact about one recipe (`generality`), whether it covers one task or several (`scope`), and whether it could be split (`decomposable`). The question is anticipated at review, not in the input.

## Principles this note holds to

1. **The prompt does not change.** An agent plays its goals as it does today. There is no explorer prompt and no instruction to learn. Distillation is a side effect of the work, and the framing is self-improvement: an agent improves from its own recorded experience. The base prompt stays a fixed variable across arms (ADR-003).
2. **The change is in the distillation process.** What a run leaves behind is already recorded: the calls with their outputs, and the model's per-turn messages and reasoning (ADR-003 §2.4, amended). The work is in what is done with it afterwards.
3. **No oracle.** Whatever is distilled comes only from what the model and the world produced: no solver output, score, or label of which calls were needed. The oracle may judge the lessons afterwards, never feed them.
4. **Distillation works from recorded procedural memory, wherever it lives, and no particular distiller has to come first.** The input is what a run records: the model's messages and reasoning, a step per turn, and the tool calls with their outputs. That is the same content whether it is read back from the memory service or from our local JSON (the run folder's `conversation.jsonl`, `trace.jsonl` and `run.jsonl`, with outputs regenerated by replay as the recording step already does). The distiller may be the memory service's generator, a bespoke lessons-learned post-process, or both for comparison. A bespoke first distillation that never calls the service is as acceptable a start as trying the service first.

## Option: the memory service's generator

One distiller worth trying, not a prerequisite for the others. What can be tried inside the current mechanism, cheaply:

- Generate from a wider scope than one goal. The service's generate call takes a scope of `workspace`, `conversations`, `entity`, `ontology_class` or `time`; today the harness always sends `conversations` for one goal's runs. A workspace or entity scope over several goals' runs may give a skill that spans them, or several skills.
- Count and read what comes back: how many skills, what each states, whether any states a rule and not a recipe.

What is not known, and worth asking the memory service's team if this route is taken: whether one call can produce several skills; whether generation generalizes across goals or only summarizes a pattern that recurs; how it treats failed runs; whether it uses a step's reasoning (an earlier question). The single-skill call is the limit of this option. Several skills means several calls over different scopes, and picking those scopes is the harness's job. If the route is not taken, nothing below waits on it.

## A lessons-learned post-process

This can be the first distillation, with no service in the loop. After a run, or a batch of runs, a review reads the recorded procedural memory and writes lessons. It reads through a small source seam with two implementations, one over the memory service's API (conversations, steps and tool calls pulled back from a workspace) and one over the local run folders, so the same review runs on either and their lessons can be compared. It is the same shape as the critic and reviser: a role with no tools, built from named inputs only, with its model and settings recorded in the cast and the loop record. A lesson is not a skill. It is a unit of what was learned:

- **A fact:** this arrangement made this item.
- **A chain:** this item is an input to that craft.
- **A rule:** a generalization, with the observations that support it and any that contradict it.
- **A caution:** a craft that burned stock, or a refusal and the constraint it stated.
- **A strategy:** what to try first, drawn from what shortened a search.

Each lesson carries its statement, **evidence** (citations to the run and call it came from, as the reviser's change record already requires), a support count, and where it applies. A lesson without evidence is refused, so the review cannot invent.

Lessons accumulate. A post-process updates a store: merging duplicates, raising the support of a repeated fact, and retiring or flagging a lesson a later observation contradicts. The memory service does this implicitly today; owning it means its inputs, its rules and its record are ours, and it does not depend on a deployment we do not control.

**Skills are packaging over lessons.** A packaging step selects lessons into one or more skills, by topic (a catalog skill, a rule skill), by goal family, or by what a student will meet. Separating learning (the lesson store), packaging (skills) and loading (retrieval) is what lets one body of experience serve several targets.

The existing critic and reviser can review a packaged skill as they do now. A lessons review is a new role; it would be specified in the harness-based-distillation ADR.

## What this means for the rest of the system

- **Experience, and held-out goals.** With "all runs are input", the runs that count as experience must be named, and must exclude any run on a held-out goal. ADR-003 keeps held-out goals out of every recording; calibration trials run on every goal, including held-out ones, and must not feed lessons, or the later unaided baseline stops being unaided. This is the main hazard. Only designated recorded arms are experience.
- **Self-improvement loops.** If a student's own runs with a skill also produce lessons, the store drifts. Each arm must name the exact snapshot of lessons it ran with (a hash, like a skill's), and the loop record names the process version.
- **Several skills for a student.** The Skill tool offers one skill today. A library needs a way to list skills with their descriptions and load one by name, and `score.json` needs the skills offered and the ones loaded. Retrieval depends on descriptions, and the 1-in-3 skill-load rate says that is not free.
- **Evaluation.** The held-out goals come in three kinds, as ADR-003's perturbed-world design already sketches: covered by a catalog entry, reachable only through a generalization, and covered by neither. Beyond a student's success, the lessons themselves can be judged against the world's real recipes, for precision (are the facts true), coverage (how much of the recipe space was found) and whether a rule holds on unseen recipes. That judging uses the oracle, and only to judge.
- **Records.** One provenance record per skill, a record of the lesson store's snapshot, and a process version for the lessons review.

## A possible order

The first two steps do not depend on each other, and step 3 does not wait on the service.

1. **Read the data already collected:** replay the logs of the invented-world calibration runs and count the distinct recipes the search found, and whether they cover the glirol and vriobeno chains. That says whether a catalog is plausible from goal-directed attempts alone. It is for judging, not feeding.
2. **Optionally, the service's generator over a wider scope** than one goal, to see how many skills come back and what they state, with the questions above if the memory team is asked.
3. **Prototype the lessons review offline** over the local run folders, with evidence citations required, and score the lessons against the world (precision, coverage), without any student. Run it over the service-pulled form too if the source seam exists, to check the two sources give the same input.
4. **Package and load:** one skill from lessons, then several, with the student arm changes above.
5. **Decide:** an ADR-003 amendment for the unit of distillation and the held-out design, and an ADR for harness-based distillation, which may replace the service as the distiller outright.

## Open questions

- How many skills before loading them costs more than it saves?
- Should the lessons review see a model's reasoning as well as its calls? Reasoning is where a generalization is stated, but it is also the most variable input.
- Which model plays the lessons reviewer, given that the cast allows the same model as teacher and student? Self-review may reinforce the model's own mistakes.
- Does a lessons store belong in the memory service as well (written back as memory), or only in the harness? Either is compatible with replacing the service as the distiller.
- Which source is the system of record for procedural memory, the local JSON or a workspace? The local JSON needs no workspace lifecycle and is what the recording step reads from today, so it is the simpler default.
- How is a lesson that holds only in one world kept from being offered in another?
