# For the memory service's team: what we record and what we found

Status: 2026-10-12, written for a meeting. Facts are from this repository's notes (`design/notes/skill-pilot.md`, ADR-001, ADR-003) and from reading the service's public OpenAPI document.

## What the harness sends today

For each teacher run: one conversation (metadata: source, run label); two messages (the prompt, the final answer); one reasoning step per distinct tool, whose reasoning is the fixed text `Claude Code ran <tool> with the provided tool input` (the same text the hooks wrote); and one tool call per call, with input, output, status (`success` or `failure`) and duration, linked to its tool's step. Outputs are regenerated by replaying a deterministic simulation, so they are exact. No recall runs during a recorded run.

## What we found

- A skill distilled from one successful run passed the quality gates (grounding 1.0, coverage 1.0) and was unhelpful: its steps replayed the teacher's exploration routine (read help, check inventory, place, clear, remove) and the recipe sat in the *why* line of the last step.
- Three Sonnet runs of the faithful world, 11 calls each with no refusals, gave skills that passed the gates and held no recipe. Coverage measures recurring patterns, which a generic workflow satisfies.
- Students loaded the skill late, never, or at an unrecorded point; the skill's description began with a tool name.
- Deleting a conversation did not remove what was extracted from it, and a graph query found its step and tool-call nodes left as orphans.
- Our hypothesis, not a finding: the distiller has no reasoning to tell a necessary call from a wrong turn (a call that returns success and goes the wrong way looks like any other), so it summarises the call pattern.

## Questions

1. **Reasoning.** Does skill generation read a step's `reasoning`, `actionTaken` and `result`, or only the tool calls and their order? Would real reasoning change what it produces? Is there a field that is meant to carry an agent's own account of why a call helped or did not?
2. **Message history.** Does generation use the conversation's messages, or only steps and tool calls? Does a conversation of two messages starve the knowledge-graph extraction that feeds long-term memory?
3. **Wrong turns.** How should a successful call that led nowhere be represented? Today status is `success`, `failure`, `error`, `timeout`, `cancelled` or `pending`. Does anything in generation weigh a call's contribution to the outcome?
4. **Exploration against procedure.** Is it intended that a skill generated from a run starts with discovery calls? Is there a way to ask for the procedure only?
5. **Contrast.** Does generation use several runs of one goal to find what they share and what differs, and is there a recommended number and mix of successes and failures?
6. **Gates.** Grounding and coverage passed on skills we judged empty. What do they measure, and is a measure of usefulness planned?
7. **Tool names.** A skill names the tools as recorded. If the agent that later loads it sees different names (here `place` against `mcp__craft__place`), is that expected to work?
8. **Model and version.** Does skill generation call a language model, and can the deployment or the request choose which? We record the service's `GET /v1/version` (version, release date, build commit, environment) with each skill; is the commit enough to identify what generated it, including any model and prompt?
9. **Cleanup and versions.** Does deleting a workspace remove its contents, and can orphaned step and tool-call nodes be removed after deleting a conversation? What changes between versions, and is there a changelog we can record with each run?

## What we are changing

The recording will carry the model's messages and per-turn reasoning and the tool names the model saw, and will carry nothing the harness concluded about the run (ADR-003 §2.4, amended 2026-10-12; spec 007 FR-028 to FR-032). We would then distil twice from the same runs, once with placeholder steps and once with real reasoning, to see whether question 1's answer shows up in the skill.
